# 框架和被测类型路由

只读取与当前系统相关的部分。目标仓库已有稳定测试框架时，沿用现有框架而不是迁移。

## Web UI

优先使用项目已有浏览器框架；无框架且使用 Python 时可选 Playwright。

- 使用语义定位器、稳定测试 ID 或可访问角色，避免脆弱层级 CSS/XPath。
- 使用条件等待，不使用固定长时间 `sleep`。
- 登录状态可安全复用时保存运行时状态；明确失效后才打开登录页面。
- UI 操作后断言最终业务状态、网络响应或持久化结果。
- 失败时保存截图、当前 URL、关键 DOM/控制台摘要，并过滤凭证。
- 若流程实际通过后端/桌面客户端完成，不为了“看起来像 E2E”额外打开网页。

## HTTP API

Python 项目可使用 `requests` 或仓库已有客户端。

- 使用结构化 JSON、schema 和明确超时。
- 区分传输成功、协议成功和业务成功。
- 认证从环境或运行时 fixture 注入。
- 对创建资源记录 ID，并仅清理本次创建的资源。
- 对重试进行幂等性分析；可能重复创建、扣费或发送时默认不自动重试。
- 覆盖授权、参数边界、冲突、限流、超时和服务端错误。

## Electron、桌面和 Socket

先搜索主进程注册事件、预加载桥、IPC/Socket handlers、平台映射和正式启动入口。

- 测试作为外部客户端调用现有 IPC 可达入口、Socket 或公开 API。
- 不直接导入生产发布函数来绕过 Electron 主流程。
- 不增加只为测试存在的生产消息或入口，除非用户明确要求设计可测试性改造。
- 事件 payload 使用 JSON/协议解析，保留任务 ID 以过滤并发消息。
- 分别设置连接、握手、准备、执行和最终状态超时。
- 服务已运行时复用；需要启动时使用隔离 profile，并只关闭测试自启进程。
- stdout 可能打印敏感完整 payload 时，采集器整段抑制该块。

例如发布工作流的通过条件通常是最终状态成功且存在业务发布 ID，而不是 `emit()` 没有报错。

## 文件、导入导出和数据处理

- 使用真实解析器，不用字符串切割代替 JSON、CSV、Excel、XML 或归档格式解析。
- 使用临时目录并校验编码、类型、边界值、重复数据和部分损坏。
- 原子输出时先写同目录临时文件，完整验证后替换目标。
- 验证内容与结构，不只检查文件存在。

## 混合流程

对“Web 登录 + Electron 执行 + API 核验”等混合系统，按所有权拆分 driver：

```text
认证 fixture -> 运行时状态
数据构建器 -> 正式 payload
业务客户端 -> 正式入口
状态观察器 -> 进度和最终结果
报告器 -> 脱敏证据
```

浏览器完成认证后应及时释放，不让无关 UI 会话贯穿后续阶段。

## 移动端和专用平台

沿用项目已有 Appium、原生测试或设备云方案。未明确设备、平台版本、签名和运行环境时，先完成可独立验证的模型/接口层，不臆造可运行的设备脚本。
