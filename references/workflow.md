# 自动化脚本生成流程

## 1. 建立事实基线

先读取：

- 用户需求、测试计划、验收条件和已知故障。
- 仓库语言、框架、依赖、启动命令和 CI 配置。
- 现有测试目录、fixture、测试数据、日志和报告约定。
- 被测功能的真实入口、下游依赖、成功状态和失败状态。
- 工作树状态，区分用户已有修改和本次任务范围。

优先使用 `rg` 搜索路由、接口、事件、组件、状态码和业务 ID。搜索不可用时再使用平台原生命令。

不要只根据 UI 文案设计测试。追踪从用户动作到最终业务状态的完整路径，并记录哪些层级可以在本地验证、哪些依赖真实环境。

## 2. 把需求转换为测试模型

对每项需求明确：

| 项目 | 要回答的问题 |
|---|---|
| 前置状态 | 账号、数据、服务、权限和环境需要什么 |
| 输入 | 用户参数、文件、API body、事件或操作序列 |
| 动作 | 调用哪个正式入口 |
| 中间状态 | 哪些进度、状态迁移或异步事件必须出现 |
| 最终断言 | 哪个业务字段或持久化状态证明成功 |
| 失败断言 | 错误类型、状态码、消息和清理行为 |
| 副作用 | 会创建、修改、发送、发布、支付或删除什么 |
| 清理 | 哪些资源可由测试安全回收 |

至少考虑正常、边界、错误、状态迁移和恢复场景。覆盖数量随风险增长，不为追求数量重复同一行为。

## 3. 选择测试层级

- 单元测试：纯函数、校验器、映射、解析、状态机。
- 合同测试：请求/响应 schema、事件名、payload、配置和数据格式。
- 集成测试：真实模块边界、数据库、消息、Socket 或本地服务。
- 端到端测试：从用户入口到最终业务状态的完整路径。

用低层测试覆盖组合和错误分支，用少量高价值 E2E 证明系统闭环。不要用大量慢 E2E 替代可确定的合同测试。

## 4. 设计测试结构

遵循仓库约定；无约定时可采用：

```text
tests/
|-- common/       认证、客户端、日志、模型
|-- config/       环境和路径配置
|-- data/         无敏感信息的测试数据
|-- utils/        数据读写、报告、通用校验
|-- test_*/       测试用例
|-- conftest.py   fixture、标记、门禁、失败附件
|-- pytest.ini
`-- requirements.txt
```

保持以下分离：

- 用例描述业务步骤，不承载复杂协议实现。
- 驱动/客户端封装交互、超时和资源释放。
- 数据层负责解析、类型、白名单、默认值和原子写入。为可维护性，默认让一个经过 schema 校验的 JSON 文件作为同一测试套件的唯一配置源；除非需求明确，否则不维护 TXT/JSON 的镜像或转换产物。
- 配置层负责环境差异，不把机器路径硬编码到用例。
- 日志层统一阶段、字段和脱敏。

## 5. 实现顺序

1. 建立最小配置和依赖。
2. 实现数据模型及校验。
3. 实现认证或前置状态 fixture。
4. 实现正式入口的测试客户端/驱动。
5. 实现一条成功闭环用例。
6. 添加合同和错误测试。
7. 增加日志、失败附件和报告。
8. 补执行文档和副作用说明。

每步先运行最窄相关测试，再运行完整默认回归。

## 6. 完成标准

- 测试能从干净环境按文档安装并收集。
- 默认回归没有未授权外部副作用。
- 成功断言基于最终业务状态，而不是仅基于调用成功。
- 失败信息能定位数据、步骤、接口/事件和原因。
- 敏感值不出现在测试源码、日志和报告。
- 资源在成功、失败和超时路径均释放。
- 报告可生成，执行结果和未覆盖风险如实交付。
